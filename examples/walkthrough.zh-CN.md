# 从画布操作到正确的修改目标

[English](walkthrough.md) · [返回项目介绍](../README.zh-CN.md) · [工程设计](../docs/architecture.zh-CN.md)

前四个案例共用 [page.tsx](page.tsx) 和 [products.json](products.json)，第 5 节将操作串成持续编辑过程。
它们是静态源码与预期结果，用于推演编辑语义；此仓库不执行渲染、分析或修改。
商品数据由假想的宿主传入 `Page`，页面通过 `featuredProductId` 选择展示对象。

## 1. 修改直接文案

用户选中页面顶部标题，希望改成“Everyday objects, thoughtfully made”。

原始源码：

```tsx
<h1>Objects for small spaces</h1>
```

预期修改：

```tsx
<h1>Everyday objects, thoughtfully made</h1>
```

编辑索引可以将文本字段定位到该 JSX 文案节点。
宿主检查选择所属版本与当前文件内容，再提交这一处替换。
`h1` 标签、周围布局、商品数据与其他文字保持不变。

这个案例中，显示值有直接且唯一的作者来源，修改计划较简单。
下一例说明为什么相同的显示文字不足以定位目标。

## 2. 只修改第二张提示卡

`Note` 的定义只有一份：

```tsx
function Note({ title }: { title: string }) {
  return (
    <aside className="note">
      <h2>{title}</h2>
    </aside>
  );
}
```

页面调用了两次，文字完全相同：

```tsx
<Note title="Made for small spaces" />
<Note title="Made for small spaces" />
```

用户只修改第二张卡片，预期结果为：

```tsx
<Note title="Made for small spaces" />
<Note title="Designed for daily use" />
```

这次选择需要经过以下解析：

```text
第二张卡片的 h2
  → Note 定义中的 title 字段
  → 当前渲染对应的第二个调用点
  → 该调用点的 title 字面量
```

静态分析确定 `title` 的传递关系，运行时观测区分当前呈现对应的调用点。
宿主验证这条关系后，修改第二个参数。按文本全局替换会同时改两张卡片；
把组件定义里的 `{title}` 改为固定字符串，也会改变所有调用者的结果。

示意命令如下。选择标识由宿主解析，实际系统中的标识应从当前索引与选择会话产生：

```json
{
  "expectedRevision": "r1",
  "selectionId": "second-note-heading",
  "field": "text",
  "operation": "set-text",
  "scope": "instance",
  "value": "Designed for daily use"
}
```

本例两个实例有独立调用点参数，因此可以直接修改源码参数。
如果多个实例共用同一个来源，编辑器需要明确选择共享修改或受支持的实例覆盖，不能自行扩大修改范围。

## 3. 更换商品，与修改商品价格

页面当前引用为：

```tsx
const featuredProductId = "cup-blue";
```

`ProductCard` 读取商品名称，并将 `priceInCents` 格式化为价格文本。
合成数据中的蓝色杯子价格为 `2400` 美分，展示结果为 `$24.00`。

### 更换展示商品

用户选择砂色托盘后，预期的项目修改是：

```tsx
const featuredProductId = "tray-sand";
```

同一份卡片代码随后读取托盘名称与价格，显示 `$32.00`。
商品数据文件不变，卡片布局不变，业务字段之间的关联仍然保留。
该示例用字面量保存引用；真实系统也可以使用有明确契约的页面设置或查询参数。

### 调整价格颜色

这是展示层修改。编辑器根据用户选择的定义级或实例级范围，修改样式或记录实例外观覆盖。
`priceInCents`、格式化表达式与商品引用都应保持不变。

### 修改真实售价

这是业务操作，应该进入商品服务的授权写入入口，使用商品自身的版本与业务规则。
将 `{formattedPrice}` 替换成 `"$20.00"` 只会生成与真实售价脱离的页面文字，不能完成业务修改。

### 修改价格格式

这是展示计算规则修改，例如变更 `Intl.NumberFormat` 的选项。
它需要明确的格式设置或代码修改入口，不能把最终显示字符串当作原始数值直接写回。

| 意图 | 应修改 | 应保留 |
| --- | --- | --- |
| 展示另一件商品 | 页面商品引用 | 商品记录、卡片代码 |
| 改价格颜色 | 已选范围内的样式 | 商品价格、引用、计算表达式 |
| 改真实售价 | 商品服务中的字段 | 页面绑定关系 |
| 改价格格式 | 格式规则 | 原始价格数值 |

## 4. Agent 修改代码后，再提交旧选择

假设画布来自项目版本 `r1`。用户已选中第二张提示卡，但尚未提交修改。
此时 Agent 为页面添加说明段落，并保存为 `r2`。

```text
r1：画布选择第二张卡片，记录选择与基准版本
    ↓
r2：Agent 增加源码，宿主提交新版本
    ↓
旧画布发送 expectedRevision = r1
    ↓
宿主发现当前版本为 r2，拒绝陈旧修改
    ↓
加载 r2 的预览与索引，重新确定目标，再形成新命令
```

即使文字没有变化，原来的偏移位置也可能已经失效。
版本检查可以阻止旧命令覆盖新源码；身份协调则帮助用户在新版本中找回可确认的原目标。

如果 Agent 复制或重排了无法区分的相同节点，系统应要求重新选择。
把“第二区域中的同样文字”自动认作旧目标，会把不确定的对应关系变成实际写入。

## 5. 串起来：Agent、商家与后台数据共同变化

这一节基于上述合成样本，说明参考设计中的状态演进与预期结果。
约定页面通过业务读取服务刷新商品数据，项目保存引用和展示设置。
`p1`、`p2` 等表示项目版本，`b1`、`b2` 表示示意的业务数据版本；它们属于不同的修改边界。

| 步骤 | 操作 | 项目版本 | 业务视图 |
| --- | --- | --- | --- |
| 初始状态 | 展示蓝色杯子，两张提示卡使用相同文案 | `p1` | `b1`：杯子 $24，托盘 $32 |
| 商家改文案 | 第二张提示卡改为 Designed for daily use | `p2` | `b1` |
| 商家改外观 | 仅当前商品卡片的价格设为紫色 | `p3` | `b1` |
| Agent 调整布局 | 为提示卡增加包裹，移动商品卡片 | `p4` | `b1` |
| 后台更新售价 | 杯子调价，业务读取随后刷新 | 仍为 `p4` | `b2`：杯子 $26，托盘 $32 |
| 商家换商品 | 当前卡片改为展示托盘 | `p5` | `b2` |
| 商家撤销换商品 | 恢复 `p4` 的项目状态，保存为新版本 | `p6` | 仍为 `b2` |

### 商家的两次修改，采用不同的保存方式

第二张提示卡有独立的字面量参数，因此修改该调用点即可，不必另存一份文案覆盖。
价格颜色要求只影响当前商品卡片，这里采用稀疏的实例样式覆盖，记录已确认的实例、字段与属性。
商品售价与 `formattedPrice` 表达式都保持不变。

**是否写源码，取决于已有来源和操作范围。** 每次画布操作都保存一层覆盖，会增加状态合成与迁移成本；
每次都修改共享定义，又可能扩大作用范围。两种修改入口需要统一进入项目的版本事务。

### Agent 调整布局，先检查哪些关系仍然成立

本例中的 Agent 从 `p3` 开始，仅调整包裹与位置，保留两个提示卡参数和商品引用。
编译过程重新生成源码位置，并检查商品卡片的实例路径与价格字段是否仍可确认。
关系成立时，价格颜色继续应用，第二张提示卡也保留新文案。

若 Agent 同时复制了无法区分的卡片，原样式覆盖可能需要重新定位；
若 Agent 明确修改了某个被内容覆盖的基础值，还需要检查旧覆盖是否已失效。
这些变化不能只用“节点 ID 没变”统一处理。

### 后台数据更新，不创建一份新的页面价格

杯子从 $24 调整到 $26 后，刷新后的业务视图经原有价格表达式产生 `$26.00`。
项目仍是 `p4`，商品卡片的实例颜色仍然有效。
编辑器应保留价格字段的业务来源，不把上次渲染的 `$24.00` 存成可持续覆盖真实价格的本地文字。

### 换商品与撤销，分别恢复什么

换成托盘时，只修改页面引用。卡片继续使用自己的外观设置，名称与价格来自托盘记录。
撤销该操作时，恢复的是杯子引用及此前项目状态；业务视图已经是 `b2`，因此页面应显示 **$26**。

这次撤销不能把杯子的真实售价改回 $24。
项目历史负责恢复项目状态，业务历史负责业务数据；呈现结果由两者按读取契约组合。

### 发布验证什么

发布 `p5` 时，发布产物应携带托盘引用、局部外观和修改后的提示卡文案。
在相同业务视图下，预览与发布对它们的解释应一致。
之后保存 `p6` 的撤销结果属于新草稿，需要按发布流程更新线上版本；业务数据仍按业务读取策略更新。

这个案例将正确性落在五个检查点：修改范围、实例覆盖适用性、代码变更后的身份对应、业务数据新鲜度，
以及项目撤销与业务写入的独立性。每一项都可以用具体前后状态验证。

## 如何用这些案例评审一个实现

对每个案例检查四件事：编辑器是否正确定位来源，是否遵守用户选择的范围，
是否保留无关源码与业务数据，以及保存、重新加载和发布后的效果是否一致。

可以补充 `.map()`、参数转发、条件分支或共享内容等例子，但应继续写明预期修改对象。
“页面看起来改对了”还不足以证明源码、数据与后续编辑保持一致。
